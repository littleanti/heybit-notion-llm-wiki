# draft-procedure — new · edit · submit 절차 상세

SKILL.md 의 요약을 실제로 수행하는 순서다. 형식의 정본은 `references/draft-templates.md` 와 저장소 `docs/DESIGN.md` 10절.

## 0. 시작 전 확인

1. 현재 디렉터리에 `notion-wiki.config.json` 이 있는가? 없으면 **멈추고** 안내한다:
   "이 디렉터리는 위키 작업 공간이 아닙니다. `notion-wiki.config.json` 을 만들거나 작업 공간에서 실행하세요."
2. 설정에서 **서비스 slug 목록**과 **카테고리 slug 목록**을 읽는다 (`services[]`, `categories[]`).
   사람에게 물을 때 이 목록을 선택지로 준다 — 자유 입력을 받으면 오타가 게시 단계까지 간다.

## 1. 입력에서 뽑아낼 것 (`new`)

준 내용을 읽고 아래를 **판단**한다. 판단의 근거가 입력에 없으면 **묻는다**.

| 항목 | 판단 근거 | 애매하면 |
|---|---|---|
| 서비스 | 입력에 서비스 이름·제품 용어가 있는가 | 묻는다 (서비스가 하나면 그것으로) |
| 카테고리 | 내용의 성격 (문의 응대 → CS, 규칙 → 법무·상품기획, 장애·구현 → 상품개발) | 묻는다 |
| 문서유형 | `draft-templates.md` 의 "이 유형을 고르는 기준" | 묻는다 |
| 제목 | 입력의 주제. "무엇에 대한 무엇" | 제안하고 확인받는다 |
| 요약 | **입력에 없으면 절대 지어내지 않는다.** 초안을 채운 뒤 본문에서 뽑아 제안하고 확인받는다 | 묻는다 |
| 담당자 | 입력에 이름이 있는가 (회의 메모의 작성자·논의 주체) | **묻는다.** 사람 이름은 추측 대상이 아니다 |
| 키워드 | 고객·실무자가 검색할 말. 입력에 나온 표현 + 영문·약어 | 제안만 하고 넘어간다 (선택 속성) |

한 번에 묻는 예 (`AskUserQuestion` 한 번, 질문 2~3개):
- "카테고리는 어디로 할까요?" → 설정의 카테고리 목록
- "담당자는 누구로 넣을까요?" → 자유 입력
- "요약을 이렇게 쓸까요?" → 제안 문장 + "다르게"

## 2. 골격 만들고 채우기 (`new`)

```
node <스크립트 디렉터리>/draft-new.js --service <slug> --category <slug> --type <문서유형> --title <제목> --owner <이름> --summary <한 문장>
```
(스크립트 디렉터리는 SKILL.md 상단의 `${CLAUDE_SKILL_DIR}/scripts` 다. 선택 인자: `--keywords a,b` `--tags a,b` `--review-by YYYY-MM-DD` `--sensitivity` `--author-type`)

그 다음 파일을 Read 하고 섹션마다 Edit 한다. 규칙:

- 안내 주석 `<!-- ... -->` 은 **지운다** (게시할 때 어차피 사라지지만, 사람이 검토할 때 방해된다).
- **입력에 있는 내용만** 쓴다. 수치·기한·금액을 입력에 없이 쓰지 않는다.
- 입력에 답이 없는 항목은 `## 미확정 · 열린 질문` 에 질문으로 옮긴다:
  `- 환불 기한을 7일로 할지 14일로 할지 (법무 확인 필요)`
- 같은 주제의 기존 원본을 찾아 근거로 단다:
  `Grep` 으로 `raw/` 에서 키워드를 찾고, 그 파일 frontmatter 의 `source_url` 을 링크로 쓴다.
  기존 원본과 **수치가 다르면** 어느 쪽도 고르지 말고 미확정에 둘 다 적는다.
- 표는 파이프 표로. 코드·명령은 코드 펜스로.

## 3. 기존 페이지 받아 오기 (`edit`)

```
node <스크립트 디렉터리>/draft-pull.js <raw 경로 | Notion URL | page id>
```

- 대상이 `raw/` 미러에 있으면 경로를 주는 것이 가장 안전하다(서비스·카테고리·본문 위치가 파일에 적혀 있다).
- 미러에 없는 페이지는 `--service`·`--category` 를 함께 준다.
- 이미 초안이 있으면 중단한다. 그 초안을 이어서 고치거나, 현재 Notion 내용으로 다시 받으려면 `--force`
  (그때 그 초안의 수정 내용은 사라진다 — 사람에게 먼저 알린다).
- 거부되는 경우(그대로 전한다): 민감 · 폐기 · 휴지통 · **하위 페이지·DB 를 가진 페이지** · 위키 루트 아래.

받아 온 본문을 고칠 때:

| 하는 것 | 하지 않는 것 |
|---|---|
| 문장·수치·항목을 고친다 | 표를 파이프 표로 바꾸기 (`<table>` 유지) |
| 섹션을 추가한다 | 탭 들여쓰기를 스페이스로 바꾸기 |
| `## 변경 이력` 에 오늘 항목을 추가한다 | `\<` `\|` 같은 이스케이프를 지우기 |
| 필수 섹션이 없으면 추가를 **제안**한다 | 레거시 문서를 템플릿에 맞춰 통째로 재구성하기 |

마지막 항목이 중요하다. `edit` 의 목적은 **요청받은 변경**이다. 구조 정리는 사람이 원할 때만 한다.

## 4. 게시 (`submit`)

```
node <스크립트 디렉터리>/draft-submit.js <초안 경로>            # dry-run (읽기만)
node <스크립트 디렉터리>/draft-submit.js <초안 경로> --apply    # 실제 게시
```

dry-run 출력을 사람에게 그대로 보여 주고, 아래를 확인한다:

1. **대상**이 의도한 데이터베이스인가 (`루틴핏 · CS` 처럼 나온다).
2. **담당자**가 `이름 → 사용자 id` 로 해석됐는가. 중단되면 이름이 워크스페이스 사용자와 다르다는 뜻이다.
3. 수정이면 **diff 가 의도한 변경만** 담고 있는가. 의도하지 않은 줄이 보이면 초안을 고친다.
4. `E` 오류는 게시를 막는다 — 고친 뒤 다시 dry-run. `W` 경고는 사람의 판단으로 넘어간다.
5. 대상이 `확정` 이면 그 사실을 말하고 **명시적 확인**을 받는다.

게시 후:

- 만들어진 페이지 URL(신규) 또는 교체 결과(수정)를 보고한다.
- `raw/` 기록 경로를 알린다. 색인·위키는 아직 낡았다 — `notion-llm-wiki` 스킬의 `ingest` 를 이어서 할지 묻는다.
- `--apply` 가 "중단:" 으로 끝나면 **아무것도 쓰이지 않았다.** 이유를 전하고 멈춘다.
- 속성은 반영됐는데 본문 교체가 실패한 경우가 있을 수 있다(호출이 둘이다). 그때 출력은 무엇이 반영됐는지 말해 준다 —
  그대로 전하고, 다시 하려면 `draft-pull` 로 새로 받으라고 안내한다.

## 5. 하지 않는 것

- 여러 페이지를 한 번에 만들지 않는다. 회의록 하나에서 FAQ 여러 개를 뽑고 싶다면, 사람에게 **하나씩** 확인받으며 진행한다.
- 페이지를 지우지 않는다. 폐기는 사람이 Notion 에서 `상태: 폐기` 로 한다.
- 위키(`wiki/`)를 건드리지 않는다. 그것은 `notion-llm-wiki` 스킬의 영역이다.
- `raw/` 를 손으로 고치지 않는다. 미러는 `submit` 과 `sync` 만 쓴다.
