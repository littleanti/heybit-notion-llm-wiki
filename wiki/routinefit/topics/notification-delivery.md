## 한눈에

- 발송은 서버 스케줄러(FCM·APNs)를 기본 경로로, 기기 로컬 알림을 백업으로 두는 하이브리드 구조다 (확정) — [알림 발송 아키텍처](../../../raw/routinefit/product-dev/알림-발송-아키텍처-555555.md)
- 발송 기준 시간대는 KST 고정이다. 해외 체류 시 현지 시각과 어긋난다 (확정) — [루틴핏 서비스 소개](../../../raw/routinefit/product-description/루틴핏-서비스-소개-555555.md)
- 2026-08-19부터 2026-08-21까지 iOS 일부 미수신 장애가 있었고 원인은 APNs 토큰 갱신 누락이다 (확정) — [iOS 알림 미수신 장애 회고 (2026-08)](../../../raw/routinefit/product-dev/iOS-알림-미수신-장애-회고-2026-08-555555.md)
- CS 응대 문서는 초안 상태다 — [알림이 안 와요 응대](../../../raw/routinefit/cs/알림이-안-와요-응대-555555.md)
- 충돌은 없다. 미확정은 로컬 알림 예약 주기와 장애 기간 보상 여부다.

## 현재 규칙 · 사실

발송 구조 (확정, 2026-08-25) — [알림 발송 아키텍처](../../../raw/routinefit/product-dev/알림-발송-아키텍처-555555.md)

1. 하이브리드를 채택한다. 서버를 기본 경로로 두고 로컬 알림을 백업으로 예약한다.
2. 서버는 FCM 과 APNs 로 KST 기준 지정 시각에 발송한다.
3. 발송 기준 시간대는 KST 로 고정하고, 서버 발송이 성공하면 로컬 알림은 취소한다.
4. 선택지 비교 — 서버 스케줄러는 시각 변경 즉시 반영(장점)과 푸시 토큰 문제 노출(단점), 기기 로컬 알림은 네트워크 없이 동작(장점)과 문구 변경·집계 불가(단점), 하이브리드는 두 경로가 서로 보완(장점)과 중복 발송 방지 필요(단점)다.

2026-08 장애 (확정, 2026-08-22) — [iOS 알림 미수신 장애 회고 (2026-08)](../../../raw/routinefit/product-dev/iOS-알림-미수신-장애-회고-2026-08-555555.md)

1. 2026-08-19부터 2026-08-21까지 iOS 사용자 일부에게 루틴 알림이 발송되지 않았다.
2. 원인은 앱 재설치와 기기 복원 이후 APNs 토큰 갱신 요청이 서버에 반영되지 않은 것이다. 만료된 토큰으로 발송이 계속 시도됐고 실패 응답을 무시하고 있었다.
3. Android 에는 영향이 없었고 기기 로컬 알림 백업은 일부만 동작했다.
4. 결정 — 토큰 갱신 실패를 오류로 처리해 재시도 큐에 넣는다, 발송 실패율 임계치 알람을 붙인다, 알림 미수신 응대 문서를 신설한다.
5. 할 일 상태 — 토큰 갱신 경로 수정은 2026-08-21 배포 완료, 응대 문서 초안 작성 완료. 발송 실패율 알람 추가와 아키텍처 문서의 백업 경로 한계 보강은 미완료다.
6. CS 문의가 사흘간 집중됐고 응대 문서가 없어 답변 문구가 담당자마다 달랐다.

로드맵에서의 위치 (확정, 2026-08-15) — [루틴핏 2026 하반기 로드맵](../../../raw/routinefit/product-planning/루틴핏-2026-하반기-로드맵-555555.md)

1. 알림 안정화가 하반기 3개 테마 중 하나이며, 범위는 알림 발송 파이프라인 재정비다.
2. 목표 지표에 알림 발송 성공률을 장애 이전 수준으로 회복·유지가 들어 있다.
3. 알림 안정화 테마는 서버 스케줄러와 기기 로컬 알림을 함께 쓰는 현재 구조를 유지한다.
4. 기획 원칙 2번은 "알림은 사용자가 정한 시각에만 보낸다. 재촉하는 알림을 임의로 추가하지 않는다" 다 (확정, 검토기한 경과) — [2025 루틴핏 기획 원칙](../../../raw/routinefit/product-planning/2025-루틴핏-기획-원칙-555555.md)
