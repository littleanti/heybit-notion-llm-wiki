## 0. 형식 설계의 원칙

이 프로젝트에서 "디자인" 은 화면이 아니라 **문서의 형식**이다. 형식은 세 독자를 동시에 만족해야 한다:
페이지를 **쓰는 사람**(형식 고민 최소), 페이지를 **읽는 사람**(Notion 에서 바로 이해),
페이지를 **읽는 Claude Code**(기계적으로 분류·요약·판별). 충돌하면 이 순서로 판단한다:

1. **작성자가 채워야 할 것은 5개를 넘지 않는다.** 나머지는 기본값·자동값·선택.
2. **판별에 쓰이는 정보는 본문이 아니라 속성(meta)에 둔다.** 본문은 사람 말로 자유롭게.
3. **"무엇이 확정이고 무엇이 미확정인가" 가 어디에서든 한눈에 보인다.** 속성 `상태` 와 본문의
   `미확정` 섹션이 그 역할이다. 위키도 같은 구분을 유지한다.
4. 그 다음에 미관.

## 1. Notion 데이터베이스 스키마

서비스 상위 페이지 아래, **카테고리마다 데이터베이스 하나**를 둔다. 이름은 `<서비스> · <카테고리>`
(예: `루틴핏 · CS`). 여섯 카테고리 DB 는 **같은 스키마**를 쓴다 — 그래야 스킬이 한 매핑으로 읽고,
실무자가 카테고리를 옮겨 다녀도 같은 화면을 본다.

> **왜 "서비스 DB 하나 + 카테고리 속성" 이 아닌가.** 그 편이 DB 수는 적다. 그러나 heybit 의 현재
> 계층이 카테고리 페이지 단위이고, 카테고리 실무자가 자기 DB 를 "자기 공간" 으로 관리하는 쪽이
> 채택률이 높다. 스킬은 어느 쪽이든 읽을 수 있게 `카테고리` 속성을 선택 속성으로 둔다
> (DB 하나로 운영하는 조직은 이 속성을 필수로 바꾸면 된다).

### 1.1 속성 표

| 속성 이름 | 타입 | 필수 | 허용값 / 형식 | 기본값 | 누가 채우나 | 왜 있는가 |
|---|---|---|---|---|---|---|
| **제목** | title | ● | 자유. "무엇에 대한 무엇" 이 드러나게 (예: `환불 처리 응대 가이드`) | — | 작성자 | 색인의 첫 열 |
| **문서유형** | select | ● | `기획서` `정책·규정` `가이드·매뉴얼` `FAQ·응대` `회의록` `결정기록` `분석·리포트` `체크리스트` `기타` | 템플릿이 정함 | 템플릿 | 유형별로 위키가 다르게 다룬다 (정책은 확정 사실, 회의록은 맥락) |
| **상태** | select | ● | `초안` `검토중` `확정` `폐기` | `초안` | 작성자·검토자 | **위키가 사실로 서술할 수 있는지**를 결정한다. `확정` 만 사실로 쓴다 |
| **요약** | rich_text | ● | **한 문장, 120자 이내.** "이 페이지를 읽으면 무엇을 알게 되는가" | — | 작성자 | 색인 한 줄이 이것으로 만들어진다. 요약이 없으면 AI 는 본문을 열어야 하고, 사람은 제목만 본다 |
| **담당자** | people | ● | 1명 이상 | 작성자 본인 | 작성자 | 질문이 생겼을 때 누구에게 가는가. 미러에는 **이름만** 남는다 |
| 작성주체 | select | ○ | `사람` `AI` `사람+AI` | `사람` (AI 템플릿은 `AI`) | 템플릿 | AI 작성 페이지는 사람이 확인하기 전까지 `초안` 을 벗어나지 못한다 (운영 규칙) |
| 키워드 | multi_select | ○ | 동의어·영문·약어 (예: `환불` `취소` `refund`) | — | 작성자 | grep 이 동의어를 못 찾는 문제를 **작성 시점에** 흡수한다 ([TRD ADR-002](./TRD.md#adr-002--rag-없이-검색-가능한-구조)) |
| 태그 | multi_select | ○ | 자유 분류 (예: `결제` `온보딩` `iOS`) | — | 작성자 | 키워드와 구분: 키워드는 "이 문서를 찾을 말", 태그는 "이 문서가 속한 주제" |
| 검토기한 | date | ○ | 날짜 | 정책·규정 템플릿은 작성일+180일 | 템플릿·작성자 | 지나면 lint 가 `stale` 로 표시. 위키가 "검토 필요" 를 붙인다 |
| 최종확인일 | date | ○ | 날짜 | — | 검토자 | 사람이 "이 내용 여전히 맞다" 고 확인한 날. 최종수정일과 다르다(오타 수정은 확인이 아니다) |
| 비밀등급 | select | ○ | `공개` `내부` `민감` | `내부` | 작성자 | `민감` 은 미러·위키·색인 어디에도 들어가지 않는다 |
| 위키제외 | checkbox | ○ | — | 해제 | 작성자 | 민감하지 않아도 위키에 넣고 싶지 않은 페이지(개인 메모 등) |
| 원본 | url | ○ | Notion 페이지 URL | — | 레거시 등록 시 | **레거시 등록 항목**임을 뜻한다. 본문은 이 URL 의 페이지에서 가져온다 (1.3) |
| 관련 페이지 | relation (자기 참조 또는 타 카테고리 DB) | ○ | — | — | 작성자 | 위키 토픽 페이지가 묶을 때 참고. 미러에는 대상 제목·URL 만 남는다 |
| 서비스 | select | ○ | 서비스 이름 | (DB 위치로 추론) | — | DB 하나로 여러 서비스를 운영하는 조직만 사용 |
| 카테고리 | select | ○ | 카테고리 이름 | (DB 위치로 추론) | — | 서비스 DB 하나로 운영하는 조직만 사용 |
| 최종수정 | last_edited_time | 자동 | — | — | Notion | 증분 동기화의 기준 |

필수 ● 5개 중 **제목·문서유형·담당자는 템플릿이 거의 채워 준다.** 실제로 작성자가 매번 쓰는 것은
**요약 한 문장**과 **상태 변경**이다.

### 1.2 DB 뷰 (권장)

| 뷰 | 필터·정렬 | 용도 |
|---|---|---|
| 전체 | 최종수정 내림차순 | 기본 |
| 확정 | 상태 = 확정 | 실무자가 "믿고 볼 것" 만 |
| 검토 필요 | 상태 ∈ {초안, 검토중} 또는 검토기한 < 오늘 | 담당자가 처리할 것 |
| AI 작성 | 작성주체 ∈ {AI, 사람+AI} 그리고 상태 = 초안 | 사람이 확인해야 할 것 |
| 레거시 등록 | 원본 비어 있지 않음 | 이관 없이 등록된 옛 페이지 |

### 1.3 레거시 페이지 등록 절차

카테고리 페이지 아래에 **이미 있는 일반 페이지**는 옮기지 않는다. 대신:

1. 같은 카테고리 DB 에서 `+ 새 항목` → 템플릿 **"레거시 등록"** 선택.
2. `원본` 에 옛 페이지의 URL 을 붙인다. `제목` 은 옛 페이지 제목과 같게(자동 완성되지 않으므로 복사).
3. `문서유형`·`상태`·`요약`·`담당자` 를 채운다. 본문은 **비워 둔다** — 본문의 단일 출처는 원본이다.
4. 옛 페이지 맨 위에 콜아웃 한 줄을 붙여도 좋다: `📌 이 페이지의 meta 는 [등록 항목](URL) 에 있습니다.` (선택)

스킬은 등록 항목의 meta 를 읽고 `원본` 을 따라가 본문을 가져온다. 위키의 출처 링크는 **원본**을
가리킨다. 여러 페이지를 한 번에 등록하려면 `register-legacy.js` 가 카테고리 페이지 하위의 일반
페이지마다 `제목 + 원본` 만 채운 항목을 만들어 준다(나머지 meta 는 사람이 채운다).

등록되지 않은 레거시 페이지도 동기화된다. 다만 meta 가 없어 색인에 `⚠ meta 없음` 으로 표시되고
lint 가 `meta-missing` 을 낸다. 위키는 이런 페이지를 **참고 정보**로만 쓴다(`확정` 이 아니므로).

### 1.4 AI 가 작성한 페이지의 규칙

- 템플릿 **"AI 초안"** 을 쓴다: `작성주체 = AI`, `상태 = 초안` 이 잠겨 있다(Notion 은 잠금 기능이
  없으므로 규칙으로 강제하고 lint 뷰 "AI 작성" 으로 감시한다).
- AI 는 `요약` 을 반드시 채운다. 본문 첫 섹션에 **"이 문서를 만든 지시(prompt)와 참고한 원본"** 을 적는다.
- 사람이 검토해 `상태` 를 `검토중`/`확정` 으로 올리고 `최종확인일` 을 찍는다. 그 전까지 위키는
  이 페이지를 `(초안)` 표기와 함께만 인용한다.

## 2. 본문 템플릿 (문서유형별)

> 이 템플릿을 **Claude Code 가 대신 채우는** 경로는 [10절](#10-초안-파일과-작성-스킬-notion-draft)에 있다.
> 유형별 필수 섹션의 기계 판독용 정본은 [10.4](#104-문서유형별-필수-섹션-정본) 표다.

Notion DB 템플릿으로 제공한다. **모든 템플릿의 공통 골격**은 세 섹션이고, 유형별로 사이에 섹션이 추가된다.

```
## 요약                       ← 속성 `요약` 과 같은 한 문장 + 필요하면 3줄 이내 보충
(유형별 섹션)
## 미확정 · 열린 질문           ← 없으면 "없음" 이라고 쓴다. 비워 두지 않는다
## 변경 이력                   ← - 2026-09-09 (김하늘) 최초 작성 / - 2026-09-20 (박서준) 환불 기한 7→14일
```

작성 규칙 (전 유형 공통):
- **날짜는 절대 날짜**(`2026-09-09`). "지난주", "다음 분기" 를 쓰지 않는다 — 위키가 언제 읽힐지 모른다.
- 다른 Notion 페이지를 말할 때는 **`@` 멘션 또는 링크**를 쓴다. 제목만 적으면 스킬이 연결하지 못한다.
- 수치·기한·금액에는 **근거(어느 결정, 어느 회의)** 를 한 줄 붙인다.
- 확정되지 않은 것은 본문에 섞지 않고 **`미확정 · 열린 질문`** 으로 내린다. 위키는 이 섹션을 "사실" 로 쓰지 않는다.
- 표는 **머리행이 있는 단순 표**만 쓴다(셀 병합·중첩 없음). 스킬이 그대로 읽는다.

### 2.1 최소 템플릿 — `회의록` `기타`

```
## 요약
## 본문
## 미확정 · 열린 질문
## 변경 이력
```

회의록의 `본문` 은 `참석`, `논의`, `결정`, `할 일(담당·기한)` 네 소제목을 권장하되 강제하지 않는다.
**`결정`** 소제목은 위키가 결정 사실을 뽑는 지점이므로 결정이 있었다면 반드시 쓴다.

### 2.2 `정책·규정` — 위키가 "사실" 로 인용하는 유형

```
## 요약
## 적용 범위                  ← 어느 서비스·어느 사용자·언제부터
## 규정                       ← 번호 목록. 한 항목 = 한 규칙. 예외는 "단," 으로 같은 항목 안에
## 근거·관련 결정             ← 결정기록·법무 검토·회의록 링크
## 예외 처리                  ← 규정대로 안 되는 경우 누가 판단하는가
## 미확정 · 열린 질문
## 변경 이력
```

`검토기한` 기본값 = 작성일 + 180일. 정책은 시간이 지나면 틀리기 쉬운데, 아무도 다시 보지 않는다.

### 2.3 `기획서`

```
## 요약
## 배경 · 문제
## 목표 · 지표
## 범위 (포함 / 제외)
## 상세
## 의존성 · 리스크
## 미확정 · 열린 질문
## 변경 이력
```

### 2.4 `FAQ·응대` — CS 가 가장 많이 쓰는 유형

```
## 요약
## 상황                       ← 고객이 어떤 말로 문의하는가 (고객의 표현 그대로. 키워드 속성에도 넣는다)
## 응대                       ← 1차 응대 문구(그대로 복사 가능하게) · 확인할 것 · 에스컬레이션 기준
## 근거 정책                  ← 정책·규정 페이지 링크 (없으면 "없음 — 정책 필요" 라고 쓴다)
## 미확정 · 열린 질문
## 변경 이력
```

`근거 정책` 이 "없음" 인 FAQ 는 위키 충돌·미확정 페이지에 **"정책 없는 응대"** 로 모인다 — 법무·기획이 봐야 할 목록이다.

### 2.5 `결정기록`

```
## 요약                       ← "무엇을 결정했다" 한 문장
## 맥락
## 선택지                     ← 표: 선택지 / 장점 / 단점
## 결정 · 이유
## 결과 · 영향 (알려진 것)
## 미확정 · 열린 질문
## 변경 이력
```

### 2.6 `가이드·매뉴얼` `체크리스트` `분석·리포트`

가이드·매뉴얼: `요약 / 대상 / 절차(번호 목록) / 자주 겪는 문제 / 미확정 / 변경 이력`.
체크리스트: `요약 / 체크 항목(- [ ]) / 미확정 / 변경 이력`.
분석·리포트: `요약 / 질문 / 데이터·방법 / 결과 / 해석·한계 / 미확정 / 변경 이력`.
"해석·한계" 를 요구하는 이유는 위키가 분석 결과를 사실로 옮길 때 한계를 함께 옮기게 하기 위해서다.

## 3. 위키 페이지 종류와 템플릿

위키 페이지는 **표준 Markdown + frontmatter** 로 `wiki/` 에 저장되고, 게시 시 Notion 형식으로 변환된다
([TRD 6.3](./TRD.md#63-libmd-notionjs--표준-md--enhanced-md)). 스킬(Claude Code)만 쓴다.

### 3.1 공통 frontmatter

```yaml
---
title: 환불 정책                 # Notion 게시 제목. 토픽은 "토픽: " 접두어가 게시 때 붙는다
type: topic                      # overview | digest | topic | conflicts
service: routinefit              # 설정의 서비스 slug. 교차 서비스 토픽은 "all"
category: cs                     # digest 에만
summary: 루틴핏 환불의 기한·조건·CS 응대 기준을 정책·CS·법무 원본에서 종합했다   # 색인 한 줄
keywords: [환불, 취소, refund]
sources:                         # 이 페이지가 근거로 삼은 raw 경로. lint L5 가 존재를 확인
  - raw/routinefit/legal/구독-환불-규정-3f9a1c.md
  - raw/routinefit/cs/환불-처리-응대-가이드-a1b2c3.md
```

### 3.2 출처 표기 규칙 (모든 위키 페이지 공통)

- **H2 섹션마다 출처 링크가 최소 1개** 있어야 한다 (lint L5). 링크는 raw 상대 경로로 쓴다:
  `[구독 환불 규정](../../raw/routinefit/legal/구독-환불-규정-3f9a1c.md)`. 게시 때 원본 Notion URL 로 바뀐다.
- 출처의 `상태` 가 `확정` 이 아니면 서술에 표기를 붙인다: `(초안)` `(검토중)` `(폐기 — 참고만)`.
  meta 가 없는 레거시 페이지는 `(meta 없음)`, 본문이 절단된 원본은 `(원본 일부 누락)`, 확정이지만 검토기한이 지난 원본은
  `(검토기한 경과)`. 표기는 겹칠 수 있다(`(초안 · 원본 일부 누락)`).
- 서술은 **원본에 있는 것만** 쓴다. 원본 간 종합·비교는 하되, 원본에 없는 결론을 만들지 않는다.
  추론이 필요하면 `> 추론:` 인용 블록으로 분리한다.
- 두 원본이 다른 말을 하면 어느 쪽도 고르지 않고 `## 충돌` 섹션(또는 충돌 페이지)에 둘 다 적는다.

### 3.3 `overview` — 서비스 개요 (서비스당 1)

```
## 이 서비스는                    ← 3~5문장. 상품설명 카테고리 원본에서
## 지금 알아야 할 것              ← 최근 30일 내 바뀐 확정 사항 5개 이내, 날짜 붙여서
## 카테고리별 입구                ← 각 다이제스트 링크 + 한 줄
## 토픽                          ← 토픽 페이지 링크 + 한 줄
## 충돌 · 미확정                  ← 개수와 링크
```

### 3.4 `digest` — 카테고리 다이제스트 (서비스 × 카테고리당 1)

```
## 핵심 사실                      ← 확정 원본에서 뽑은 "지금 유효한" 사실. 번호 목록, 항목마다 출처. 충돌은 항목 끝에 ⚠ 인라인 + conflicts 링크
## 진행 중 · 초안                 ← 초안·검토중 원본 요지. (초안)/(검토중) 표기, AI 작성이면 함께
## 자주 찾는 페이지              ← 원본 링크 5~10개(원본이 그보다 적으면 전부) + 한 줄 (요약 속성 그대로). meta 없는 레거시는 (meta 없음) 으로 여기에
## 검토 필요                      ← 검토기한 경과, 폐기 표시됐지만 다른 페이지가 참조 중, meta 없음, 충돌
## 미확정 · 열린 질문             ← (선택) 이 카테고리 원본들의 미확정 요지
## 관련 토픽
```

다이제스트는 **길이 상한 200줄**. 넘치면 토픽으로 뽑아낸다 (스킬 규칙). 다이제스트에는 `## 충돌` 절이 없다 — 충돌은 인라인 표기와 검토 필요, 그리고 충돌 페이지에 둔다.

### 3.5 `topic` — 토픽 (기준: 원본 2개 이상 · 카테고리 2개 이상에 걸친 주제 — 최소 조건이지 의무는 아니다)

```
## 한눈에                         ← 5줄 이내. 결론부터. 충돌이 있으면 첫 줄이 "⚠ 충돌 있음 — 아래 충돌 절 참조"
## 현재 규칙 · 사실               ← 확정 원본 종합. 항목마다 출처·날짜
## 카테고리별 관점                ← 기획은 / CS 는 / 법무는 — 같은 주제를 각자 어떻게 다루는가
## 충돌                           ← 있으면. 없으면 "없음"
## 미확정                         ← 원본의 미확정 섹션들을 모은다
## 이력                           ← 이 주제의 결정이 언제 어떻게 바뀌었나 (변경 이력 섹션들에서)
```

### 3.6 `conflicts` — 충돌 · 미확정 (서비스당 1)

```
## 충돌                           ← 표: 주제 / A 는 이렇게 (출처·상태·최종수정) / B 는 이렇게 (출처·상태·최종수정) / 발견일 / 비고(어느 쪽이 최신·확정인가 — 사실만)
                                    충돌이 없으면 "없음" + 대조한 값의 표(검증했다는 증거)
## 정책 없는 응대                 ← FAQ·응대 중 근거 정책이 "없음" 으로 시작
## 검토기한 경과                  ← 표: 페이지 / 담당자 / 기한
## meta 없음                      ← 등록되지 않은 레거시 페이지 목록
## 폐기됐지만 참조됨              ← 폐기 페이지를 확정 페이지가 링크하는 경우
## 미확정                         ← 토픽에 속하지 않는 원본들의 미확정 사항
```

이 페이지는 **사람이 원본을 고쳐야 할 목록**이다. 위키가 스스로 해소하지 않는다.
템플릿의 절을 빼지는 않되, 필요한 절을 **추가**하는 것은 허용된다.

## 4. raw frontmatter ↔ Notion 속성 매핑

raw 파일은 **frontmatter(meta) + 빈 줄 + 본문(Notion 이 준 enhanced markdown 그대로)** 이다.

```yaml
---
notion_id: 3f9a1c2b-…                       # 대표 페이지 id (등록 항목이면 등록 항목의 id)
title: 구독 환불 규정
service: routinefit                          # slug
service_name: 루틴핏
category: legal                              # slug
category_name: 법무
doc_type: 정책·규정
status: 확정
author_type: 사람
owner: [김하늘]                              # people → 이름만
summary: 루틴핏 구독 환불의 기한(결제 후 7일)·조건·예외를 정한다
keywords: [환불, 취소, refund, 청약철회]
tags: [결제, 구독]
review_by: 2027-03-01
verified_at: 2026-09-01
sensitivity: 내부
related: [{ title: 환불 처리 응대 가이드, url: https://www.notion.so/… }]
source_url: https://www.notion.so/…          # 본문이 있는 페이지 (원본). 위키 출처 링크가 가리키는 곳
registry_url: https://www.notion.so/…        # 레거시 등록 항목 (있을 때만)
meta_source: registry                        # properties | registry | inferred
created_time: 2026-06-12T09:30:00.000Z
last_edited_time: 2026-09-01T02:11:45.000Z
synced_at: 2026-09-09T01:00:00.000Z
notion_truncated: false
notion_unknown_blocks: 0
---

<!-- notion: 파일·이미지 URL 은 1시간 후 만료된다. 필요하면 Notion 에서 다시 연다 -->
## 요약
…(본문)
```

- `meta_source: inferred` 는 등록되지 않은 레거시 페이지다. `doc_type`·`status`·`summary`·`owner` 가 비어 있고
  `category` 는 조상 페이지 제목에서 추론했다.
- `owner` 가 비면 `[]`, 날짜가 비면 키를 **생략하지 않고 `null`** 로 둔다 (lint 가 "없음" 과 "형식 오류" 를 구분).
- 값의 순서와 키 이름은 고정이다 — 골든 비교와 diff 가독성을 위해.

## 5. `index.md` 와 `log.md`

### 5.1 `wiki/index.md` — 스크립트가 생성. 손으로 고치지 않는다

```markdown
# 색인

- 동기화: 2026-09-09T01:00:00.000Z · raw 33 · wiki 24
- 읽는 법: 위키 → 원본 순서로 찾는다. `⚠` 는 meta 없음, `(초안)` 은 확정 아님, `⏰` 는 검토기한 경과(2026-09-09 기준)

## 위키

```

한 줄 = `- [제목](경로) · 유형 · 상태 · 담당 · 최종수정 — 요약 · 키워드: …`. 요약이 없으면 `— (요약 없음)`.
정렬: 설정의 서비스 순 → 카테고리 순 → 제목. **입력만으로 결정된다** — 생성 시각을 담지 않고(git 이 기록), `⏰` 의 기준일은 벽시계가 아니라
마지막 동기화 날짜다. 그래서 CI 가 색인을 다시 만들어 diff 로 "갱신을 잊었는지" 를 검사할 수 있다 ([TRD 6.4](./TRD.md#64-build-indexjs), [LOG P9](./LOG.md)).

### 5.2 `wiki/log.md` — 스킬이 덧붙인다 (append-only, 최신이 아래)

```markdown

- 갱신: routinefit/digest/legal.md, routinefit/digest/cs.md, routinefit/conflicts.md, moneynote/digest/marketing.md
- 판단: 프로모션 페이지는 `초안` 이라 다이제스트 "진행 중" 에만 넣음
```

`index.md` 와 달리 `log.md` 는 **왜** 를 남긴다. 다음 ingest 를 하는 Claude Code 가 지난 판단을 읽는다.

## 8. 이름 규칙

- **서비스·카테고리 slug**: `^[a-z0-9-]+$`, 설정에서 정한다.
- **raw 파일명**: `sanitize(제목) + '-' + notion_id 앞 6자 + '.md'`.
  `sanitize` = NFC 정규화 → 공백·`/`·`\`·`:`·`*`·`?`·`"`·`<`·`>`·`|` → `-` → 연속 `-` 축약 → 앞뒤 `-` 제거 → 60자 절단.
  한글은 그대로 둔다(grep 가독성). 6자 접미어가 같은 제목의 충돌을 막는다.
- **wiki 파일명**: `overview.md`, `digest/<category-slug>.md`, `topics/<영문-kebab>.md`(스킬이 정함, 한글 금지 —
  토픽은 URL 로도 언급되므로), `conflicts.md`.
- **Notion 게시 제목**: overview → `개요`, digest → `<카테고리명> 다이제스트`, topic → `토픽: <title>`,
  conflicts → `충돌 · 미확정`, index → 설정 `indexTitle`(기본 `색인`), log → `변경 이력`.

|---|---|

| 위키 루트가 서비스 하위 | `설정 오류: wiki.rootPageId 가 서비스 "<name>" 의 하위입니다. 위키가 자기 출력을 다시 수집하게 되므로 거부합니다.` |

| dry-run 요약 | `dry-run: 생성 3 · 교체 5 · 변경 없음 10 · 고아 게시 페이지 1. 실제로 쓰려면 --apply` |
| sync 요약 | `sync: 추가 2 · 변경 3 · 이동 0 · 삭제 1 · 제외 2(민감 1, 위키제외 1) · 실패 0 · 호출 9회 · 12.3초` |
| lint 요약 | `lint: 결함 4 (meta-missing 2, stale 1, source-missing 1) → 종료 코드 1` / `lint: 결함 없음` |
| 초안 검증 실패 | `중단: 초안 검증 오류 2건 — 고친 뒤 다시 실행하세요. 아무것도 쓰지 않았습니다.` |
| 초안 dry-run 요약 | `dry-run: 신규 1 · 수정 0 · 오류 0 · 경고 1. 실제로 쓰려면 --apply` |
| 초안 게시 요약 | `submit: 생성 1 · 속성 수정 0 · 본문 교체 0 · raw 기록 1 · 오류 0` |
| 원본이 초안 이후 수정됨 | `중단: 원본이 초안을 만든 뒤에 수정됐습니다 (초안 기준 <base>, 현재 <now>). draft-pull 로 다시 받아 고치세요. 아무것도 쓰지 않았습니다.` |
| 민감 페이지 | `중단: 대상 페이지의 비밀등급이 "민감" 입니다. 이 스킬은 민감 페이지를 다루지 않습니다.` |
| 폐기 페이지 | `중단: 대상 페이지의 상태가 "폐기" 입니다. 사람이 Notion 에서 상태를 되돌린 뒤에 고치세요.` |
| 하위 페이지 포함 | `중단: 대상 페이지가 하위 페이지·데이터베이스를 갖고 있어 본문을 교체하면 함께 지워집니다 (Notion API 제약). Notion 에서 직접 고치세요.` |
| 대상이 위키 페이지 | `중단: 대상 페이지가 위키 루트 아래입니다. 위키 페이지는 publish 가 관리합니다 — 원본을 고치고 ingest 를 다시 하세요.` |
| 담당자 미발견 | `중단: 담당자 "<이름>" 을 워크스페이스 사용자에서 찾을 수 없습니다. 이름을 정확히 쓰거나, 사람이 Notion 에서 지정하세요.` |
| 담당자 동명이인 | `중단: 담당자 "<이름>" 과 이름이 같은 사용자가 2명입니다. 사람이 Notion 에서 지정하세요.` |

## 10. 초안 파일과 작성 스킬 (`notion-draft`)

4·5절이 Notion 을 **읽어** 만드는 형식이라면, 이 절은 **쓰기 위해** 만드는 형식이다.
왜 이렇게 나눴는지는 [TRD ADR-010](./TRD.md#adr-010--작성-기능은-별도-스킬-lib-는-형제-스킬에서-공유)·[ADR-011](./TRD.md#adr-011--기존-페이지를-고치는-경로의-안전-모델),
모듈 계약은 [TRD 6.8~6.11](./TRD.md#68-draft-newjs--골격-초안-만들기).

### 10.1 흐름과 세 가지 원칙

```
신규:  사람의 입력 ─→ (빠진 필수 속성은 질문) ─→ drafts/…md ─→ 사람이 검토·수정
                                                                    └→ submit(dry-run) ─→ submit --apply ─→ Notion DB 항목 + raw/ 기록
수정:  대상 지정 ─→ pull(현재 속성·본문) ─→ drafts/…md ─→ 사람+Claude 가 수정
                                                                    └→ submit(dry-run: diff) ─→ submit --apply ─→ 본문 교체 + raw/ 갱신
```

1. **Notion 에 쓰는 곳은 `submit --apply` 하나뿐이다.** `new`·`edit`(pull)·dry-run 은 읽기만 한다.
2. **초안은 평범한 마크다운 파일이다.** 검토는 사람이 에디터에서 한다 — 전용 UI 도, Notion 왕복도 필요 없다.
3. **신규 페이지는 `상태: 초안` 으로만 만들어진다** ([1.4](#14-ai-가-작성한-페이지의-규칙)). 확정은 Notion 에서 담당자가 한다.

### 10.2 초안 파일의 위치와 이름

| 종류 | 경로 |
|---|---|
| 신규 | `drafts/<service-slug>/<category-slug>/<sanitize(제목)>.md` |
| 수정 | `drafts/<service-slug>/<category-slug>/<sanitize(제목)>-<대상 id 앞 6자>.md` |

- `sanitize` 는 [8절](#8-이름-규칙)의 raw 파일명 규칙과 같다. 수정본에 id 접미어를 붙이는 이유는 같은 제목의 신규 초안과 섞이지 않게 하기 위해서다.
- `drafts/` 는 **작업 공간**이다. 게시한 뒤 지워도 되고 남겨도 된다. 남긴 초안으로 다시 게시하려 하면 `base_last_edited_time` 이 낡아 중단된다 — 그때는 `pull` 을 다시 한다.
- 위치는 설정 `paths.drafts` 로 바꿀 수 있다(기본 `drafts`).

### 10.3 초안 frontmatter

키 순서는 고정이다. `—` 는 그 종류에서 쓰지 않는 키다.

| 키 | 신규 | 수정 | 뜻 |
|---|---|---|---|
| `kind` | `new` | `edit` | 이 값이 검증·제출 경로를 정한다 |
| `service` · `category` | ● | ● | 설정의 slug. 수정에서도 적는다(파일 위치와 raw 경로가 이것으로 정해진다) |
| `title` | ● | ● | Notion 제목 |
| `doc_type` · `status` · `summary` · `owner` | ● | ● | 필수 속성 5개의 나머지. `owner` 는 **이름 배열** — 제출 때 사용자 id 로 해석된다 |
| `author_type` | ● (`사람+AI`) | 원본 값 | AI 가 손댄 페이지임을 남긴다 (1.4) |
| `keywords` · `tags` · `review_by` · `verified_at` · `sensitivity` · `exclude` · `related` | 선택 | 원본 값 | 1.1 의 선택 속성. 비우면 Notion 에도 비운다 |
| `drafted_at` | ● | ● | 초안을 만든 시각 (ISO) |
| `target_meta_id` | — | ● | **속성**을 쓸 페이지. 등록 항목이면 등록 항목의 id |
| `target_body_id` | — | ● | **본문**을 교체할 페이지. 등록 항목이면 `원본` 의 id (둘이 다를 수 있다) |
| `source_url` · `registry_url` | — | ● | 사람이 눌러서 확인할 수 있게 |
| `base_last_edited_time` | — | ● | 초안을 만든 시점의 대상 최종수정. **낙관적 잠금의 기준** |
| `base_hash` | — | ● | 받은 본문의 sha256. "본문을 고치지 않았다" 를 판정한다 |

**수정 초안의 본문은 Notion 이 준 enhanced markdown 그대로다** — 표는 `<table>` 태그, 들여쓰기는 탭, `\<` 같은 이스케이프가 들어 있다.
이 형식을 유지해야 한다. 제출 때 정규화기를 다시 돌리지 않기 때문이다([TRD 6.9](./TRD.md#69-draft-pulljs--기존-페이지를-초안으로)).
신규 초안의 본문은 **표준 마크다운**이고, 제출 때 정규화기가 Notion 형식으로 바꾼다.

### 10.4 문서유형별 필수 섹션 (정본)

[2절](#2-본문-템플릿-문서유형별)의 템플릿을 기계 판독용으로 정리한 표다. `lib/doc-templates.js` 가 이 표의 사본이고 T23 이 대조한다.
순서도 포함이며, 필요한 섹션을 **추가**하는 것은 허용된다(빼는 것은 안 된다).

| 문서유형 | 필수 H2 섹션 (순서대로) |
|---|---|
| `기획서` | 요약 · 배경 · 문제 / 목표 · 지표 / 범위 (포함 / 제외) / 상세 / 의존성 · 리스크 / 미확정 · 열린 질문 / 변경 이력 |
| `정책·규정` | 요약 / 적용 범위 / 규정 / 근거·관련 결정 / 예외 처리 / 미확정 · 열린 질문 / 변경 이력 |
| `가이드·매뉴얼` | 요약 / 대상 / 절차 / 자주 겪는 문제 / 미확정 · 열린 질문 / 변경 이력 |
| `FAQ·응대` | 요약 / 상황 / 응대 / 근거 정책 / 미확정 · 열린 질문 / 변경 이력 |
| `회의록` | 요약 / 본문 / 미확정 · 열린 질문 / 변경 이력 |

| `체크리스트` | 요약 / 체크 항목 / 미확정 · 열린 질문 / 변경 이력 |

### 10.5 검증 규칙

`E` 는 제출을 막고, `W` 는 보여 주기만 한다. 등급이 두 개인 항목은 `신규/수정` 순이다.

| 코드 | 등급 | 조건 |
|---|---|---|
| `draft-frontmatter-invalid` | E | frontmatter 를 읽을 수 없다, 또는 `kind` 가 `new`·`edit` 이 아니다 |
| `draft-scope-unknown` | E | `service`·`category` 가 설정의 slug 에 없다 |
| `draft-meta-missing` | E | 필수 5개(`title`·`doc_type`·`status`·`summary`·`owner`) 중 빈 값이 있다 |
| `draft-value-invalid` | E | `doc_type`·`status`·`author_type`·`sensitivity` 가 설정 허용값 밖이다 |
| `draft-summary-long` | E | `summary` 가 120자를 넘는다 (색인 한 줄이 이것으로 만들어진다) |
| `draft-date-invalid` | E | `review_by`·`verified_at` 이 `YYYY-MM-DD` 가 아니다 |
| `draft-body-empty` | E | 본문이 없다 |
| `draft-section-missing` | E / W | 10.4 의 필수 섹션이 없다(또는 순서가 다르다). 수정은 경고다 — 템플릿을 따르지 않는 레거시가 있다 |
| `draft-section-empty` | W | 섹션이 있으나 내용이 비었다. `없음` 도 내용이다([2절](#2-본문-템플릿-문서유형별)) |
| `draft-history-missing` | E | `## 변경 이력` 에 **오늘 날짜** 항목(`- YYYY-MM-DD …`)이 없다. 수정에서 **본문이 그대로면**(`base_hash` 일치) 요구하지 않는다 — 기록할 변경이 없다 |
| `draft-status-not-draft` | E / — | 신규인데 `status` 가 `초안` 이 아니다 (10.1 원칙 3) |
| `draft-target-missing` | — / E | 수정인데 `target_body_id`·`base_last_edited_time` 이 없다 |
| `draft-unchanged` | — / W | 속성·본문 모두 바뀌지 않았다 — 게시할 것이 없다 |

### 10.6 dry-run 리포트

```
draft-submit: drafts/routinefit/cs/알림-미수신-1차-응대.md
대상    루틴핏 · CS
동작    신규 생성
속성    제목      알림 미수신 1차 응대
        문서유형  FAQ·응대
        상태      초안
        담당자    박서준 → aaaaaaaa-0000-4000-8000-000000000003
        요약      푸시 알림이 오지 않는다는 문의의 1차 응대와 확인 순서를 정한다
        키워드    알림, 푸시, 미수신
본문    2,481 bytes · 섹션 6
경고    W draft-section-empty: `## 미확정 · 열린 질문` 이 비었다
dry-run: 신규 1 · 수정 0 · 오류 0 · 경고 1. 실제로 쓰려면 --apply
```

수정이면 `동작` 줄에 대상 상태를 함께 적고(`본문 교체 (대상 상태: 확정 — 주의)`), `속성 변경` 표와 **본문 diff**(문맥 2줄)를 보여 준다.
확정 페이지를 고치는 경우 스킬은 diff 를 보여 준 뒤 **운영자의 확인을 받고** `--apply` 한다.

### 10.7 기존 페이지 수정의 안전 거부

`pull` 과 `submit` 둘 다에서 검사한다(고칠 수 없는 페이지로 사람을 데려가지 않기 위해 `pull` 에서 먼저 막는다).
문구 정본은 [9절](#9-리포트메시지-문구-정본) 표에 있다.

| 조건 | 왜 |
|---|---|
| 초안 이후 원본의 `last_edited_time` 이 바뀜 | 다른 사람의 편집을 통째로 지운다 (낙관적 잠금) |
| 비밀등급 `민감` | 이 도구는 민감 페이지를 다루지 않는다 (DR) |
| 상태 `폐기` | 되살리는 판단은 사람이 한다 |
| 본문에 `<page url=` 또는 `<database url=` | 본문 교체가 하위 페이지·DB 를 함께 지운다 ([TRD N5](./TRD.md#31-notion-api--문서로-확인한-사실-2026-09-09-n15n16-은-2026-09-10)). `allow_deleting_content` 는 켜지 않는다 |
| 휴지통 | 대상이 아니다 |
| 위키 루트 아래 | 위키 페이지는 `publish` 가 소유한다 |

### 10.8 게시 후 `raw/` 즉시 반영

`--apply` 가 성공하면 그 페이지만 미러에 기록한다:

1. `GET /v1/pages/{id}`(속성·URL·시각) + `GET /v1/pages/{body}/markdown`(본문) 을 다시 읽는다 — **Notion 이 실제로 저장한 것**을 기록한다.
2. `raw/<service>/<category>/<파일명>.md` 를 4절 형식으로 쓴다. `synced_at` 은 이 시각, `meta_source` 는 `properties`(등록 항목이면 `registry`).
3. `raw/.sync-state.json` 의 `pages` 에 항목을 추가·갱신한다. **`syncedAt`(마지막 전체 동기화)은 바꾸지 않는다** —
   이 작업은 전체 동기화가 아니다. 그래서 색인 헤더의 동기화 시각은 그대로이고, 파일의 `synced_at` 만 새롭다.
4. 다음 `sync` 는 이 페이지를 "변경 없음" 으로 판정한다(markdown 호출 0건). 이것이 A21 이다.

색인(`wiki/index.md`)과 위키는 **자동으로 갱신하지 않는다.** 게시 후 스킬이 "`build-index` 를 돌릴지, `ingest` 로 위키에 반영할지" 를 운영자에게 묻는다 —
위키 합성은 `notion-llm-wiki` 스킬의 일이고, 이 스킬은 경계를 넘지 않는다.
