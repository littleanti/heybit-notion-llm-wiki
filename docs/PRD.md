# PRD — heybit-notion-llm-wiki

- 문서 버전: 0.1 (2026-09-09) — P0 초안. 구현·검증 결과에 따라 갱신한다
- 문서 역할: **무엇을 · 왜** 만드는가
- 관련 문서: [TRD](./TRD.md) · [DESIGN](./DESIGN.md) · [PLAN](./PLAN.md) · [LOG](./LOG.md)

---

## 1. 제품 정의

**Notion 에 쌓이는 실무 문서를 Claude Code 가 읽어 "LLM wiki" 로 합성하고, 그 위키를 다시
Notion 에 게시하며, 실무자의 질문에 RAG 없이 답하는 — Claude Code 스킬과 운영 규약의 묶음.**

세 가지를 한 저장소에 담는다:

1. **실무 페이지 작성 규약** — 앞으로 Notion 실무 페이지를 어떻게 써야 사람과 AI 모두가
   빨리 찾을 수 있는가 (Notion 데이터베이스 스키마 + 본문 템플릿 + 레거시 페이지 등록 방법).
2. **LLM wiki 의 구조와 운영 절차** — 원본(raw) / 위키(wiki) / 색인(index) / 이력(log) 의
   계층, 위키 페이지의 종류와 상한, 신선도·모순 처리 규칙.
3. **동작하는 스킬** — `.claude/skills/notion-llm-wiki/`: Notion→Markdown 동기화,
   위키 합성 절차, 질의 절차, lint, Markdown→Notion 게시. 스크립트는 Node.js 로 작성하고
   외부 의존성 0개, Notion 토큰 없이도 fixture 로 전 기능을 테스트할 수 있다.

**위키를 만드는 주체도, 검색하는 주체도 Claude Code 다.** 별도 LLM 엔드포인트, 벡터 DB,
임베딩 파이프라인을 두지 않는다. 검색은 **색인 1장 → 위키 페이지 → 원문 grep** 의 3층 경로로
한다 ([TRD ADR-002](./TRD.md#adr-002--rag-없이-검색-가능한-구조)).

## 2. 배경 — 왜 이 프로젝트가 존재하는가

### 2.1 현재 상태 (가정)

heybit 의 Notion 은 다음 계층으로 구성돼 있다:

```
[서비스 A 상위 페이지]
 ├─ [상품기획]  ── 실무 페이지 × N   (사람·AI 작성)
 ├─ [상품설명]  ── 실무 페이지 × N
 ├─ [상품개발]  ── 실무 페이지 × N
 ├─ [CS]        ── 실무 페이지 × N
 ├─ [법무]      ── 실무 페이지 × N
 ├─ [마케팅]    ── 실무 페이지 × N
 └─ (상위 페이지 바로 아래에도 실무 페이지가 있음)
[서비스 B 상위 페이지]
 └─ ... (같은 구조)
```

실무 페이지는 사람이 쓰기도 하고 AI 가 쓰기도 한다. 형식은 통일돼 있지 않다.
규모는 **수십~수백 페이지**를 상정한다 (사용자 확인, 2026-09-09).

### 2.2 문제

- **찾기 어렵다.** Notion 검색은 제목·본문 키워드 일치에 의존하고, "환불" 로 검색하면
  "취소 정책", "refund" 로 쓰인 페이지는 나오지 않는다. 카테고리를 가로지르는 질문
  ("이 서비스의 환불 규정은 무엇이고, CS 응대 문구와 법무 검토 결과는 일치하는가") 은
  세 카테고리를 각자 열어 사람이 종합해야 한다.
- **무엇이 최신인지 모른다.** 같은 주제의 페이지가 여러 개 있고, 어느 것이 확정이고 어느 것이
  폐기된 초안인지 페이지만 봐서는 알 수 없다. AI 가 쓴 페이지는 특히 그렇다.
- **AI 에게 물어도 근거를 못 댄다.** Notion 전체를 AI 에 넘길 수 없고(컨텍스트 한계),
  일부만 넘기면 무엇을 넘겼는지에 답이 좌우된다. RAG 를 붙이면 인프라(임베딩·벡터 DB·청킹)가
  생기고, 청킹은 페이지 구조와 메타 정보를 잃는다.

### 2.3 접근 — "LLM wiki" 패턴

문서를 **매 질문마다 다시 읽고 요약하는** 대신, 한 번 읽어 **LLM 이 유지하는 위키**로 합성해
두고 그 위키를 검색·갱신한다. 이 패턴의 핵심 구성은 다음과 같다:

| 계층 | 무엇 | 누가 쓰나 | 변경 규칙 |
|---|---|---|---|
| **raw** | 원본 실무 페이지의 Markdown 미러 | 동기화 스크립트 | 사람·AI 가 **Notion 에서만** 수정. 미러는 손대지 않는다 |
| **wiki** | 원본을 읽고 합성한 페이지 (다이제스트·토픽·비교) | Claude Code (스킬) | 스킬만 쓴다. 사람은 원본을 고치거나 코멘트로 요청 |
| **index** | 모든 페이지의 한 줄 요약 색인 | 스크립트 + 스킬 | 자동 생성 |
| **log** | 위키가 왜 어떻게 바뀌었는지 | 스킬 | 추가만 (append-only) |
| **schema** | 위 규칙을 적은 문서 — 스킬이 매번 먼저 읽는다 | 사람 | 드물게 |

> 이 패턴은 2026년 초 Andrej Karpathy 가 공개적으로 정리한 "LLM Wiki" 아이디어
> (raw 는 불변, wiki 는 LLM 이 유지, index/log 로 탐색과 이력, lint 로 건강 점검)를
> Notion 이라는 원본 저장소와 Claude Code 라는 실행 주체에 맞춰 구체화한 것이다.
> 구체화 과정에서 무엇을 그대로 두고 무엇을 바꿨는지는 [TRD 1절](./TRD.md#1-목표와-비목표)에 적는다.

### 2.4 이 저장소가 "샘플" 인 이유

이 저장소는 실제 heybit Notion 에 연결돼 있지 않다. **가상 서비스 2개** (`루틴핏`, `머니노트`),
**가상 실무 페이지 약 30개**로 raw 계층을 채우고, 그 위에 위키를 실제로 합성해 둔다.
독자는 (1) 규약 문서를 읽고, (2) 샘플 위키를 열어 결과물의 형태를 보고, (3) 스킬을 자기
Notion 에 연결해 쓸 수 있다. 자매 저장소 `heybit-dynamic-sample` 과 같은 그라운드 룰
([`CLAUDE.md`](../CLAUDE.md)) — 3단 사고 절차와 문서 선행 워크플로 — 로 만든다.

## 3. 대상 사용자

| # | 사용자 | 하고 싶은 것 | 이 프로젝트에서 얻는 것 |
|---|---|---|---|
| U1 | **실무자** (상품기획·상품설명·상품개발·CS·법무·마케팅) | 필요한 정보를 빨리 찾는다. Notion 에서 직접 보든, AI 에게 물어보든 | Notion 의 위키 트리(사람용) + Claude Code 질의(AI용). 둘 다 **출처 링크**가 붙는다 |
| U2 | **페이지 작성자** (사람 또는 AI) | 문서를 남기되 형식 고민은 최소화 | Notion DB 템플릿 하나 고르고 필수 속성 5개만 채우면 끝 ([DESIGN 1절](./DESIGN.md#1-notion-데이터베이스-스키마)) |
| U3 | **위키 운영자** (Claude Code 를 실행하는 사람) | 주기적으로 동기화·합성·게시하고, 위키의 건강을 확인 | 스킬 서브커맨드 5개 (`sync`/`ingest`/`query`/`lint`/`publish`) 와 운영 절차 |
| U4 | **읽는 사람** (이 저장소를 학습 자료로 보는 사람) | "LLM wiki 를 Notion 위에 어떻게 올리는가" 를 판단 근거와 함께 이해 | `docs/` 전체 + 샘플 raw/wiki |

명시적으로 대상이 **아닌** 것: 권한(ACL)에 따라 답을 다르게 줘야 하는 조직. 이 샘플의 위키는
**동기화 대상 페이지 전체가 위키 독자 전체에게 열려 있다**고 가정한다 (→ 5절 DR3, 8절).

## 4. 기능 요구사항 (FR)

### FR1 — 실무 페이지 작성 규약 (템플릿 + meta)

앞으로 작성되는 실무 페이지가 **사람과 AI 가 같은 방식으로 분류·요약·판별**할 수 있게 한다.

- **FR1.1** 서비스 상위 페이지 아래, **카테고리별 Notion 데이터베이스** 를 둔다
  (예: `루틴핏 / 상품기획 DB`). 신규 실무 페이지는 이 DB 의 항목으로 만든다.
- **FR1.2** DB 속성(= meta)은 [DESIGN 1절](./DESIGN.md#1-notion-데이터베이스-스키마)의 스키마를
  따른다. **필수 5개**(제목·문서유형·상태·요약·담당자)와 선택 속성으로 나누고, 필수가 비면
  lint 가 지적한다.
- **FR1.3** 본문은 문서유형별 템플릿([DESIGN 2절](./DESIGN.md#2-본문-템플릿-문서유형별))을 따른다.
  템플릿은 Notion DB 템플릿 기능으로 제공해 **작성자가 형식을 외울 필요가 없게** 한다.
  회의록처럼 가벼운 유형은 섹션 3개(요약·본문·변경이력)로 끝난다.
- **FR1.4** **레거시 페이지**(이미 카테고리 페이지 아래에 일반 페이지로 존재하는 것)는
  **옮기지 않는다.** 대신 같은 카테고리 DB 에 **등록 항목**(meta + `원본` 링크)을 하나 만든다.
  동기화기는 등록 항목의 meta 를 읽고 `원본` 링크를 따라가 본문을 가져온다.
  본문의 단일 출처는 원본 페이지 하나로 유지된다 (사용자 결정, 2026-09-09;
  → [TRD ADR-003](./TRD.md#adr-003--meta-는-어디에-두는가)).
- **FR1.5** AI 가 작성한 페이지는 `작성주체 = AI` 로 표시하고, 사람이 확인하기 전까지
  `상태 = 초안` 을 벗어나지 못한다. 위키는 `초안` 을 **참고 정보로만** 취급하고 확정 사실로
  서술하지 않는다.

### FR2 — Notion → Markdown 동기화 (raw 미러)

- **FR2.1** 설정 파일에 적힌 서비스 상위 페이지들을 루트로, **하위 페이지·하위 데이터베이스를
  재귀적으로** 내려받아 `raw/<서비스>/<카테고리>/<slug>.md` 로 저장한다.
  DB 속성은 frontmatter 로, 본문 블록은 Markdown 으로 변환한다.
- **FR2.2** **증분 동기화**: 페이지의 `last_edited_time` 이 이전 동기화 기록과 같으면
  내려받지 않는다. 상태는 `raw/.sync-state.json` 에 남긴다.
- **FR2.3** `비밀등급 = 민감` 이거나 `위키제외` 가 체크된 페이지는 **내려받지 않는다.**
  이미 미러에 있던 것이 민감으로 바뀌면 미러에서 **삭제**한다.
- **FR2.4** Notion 에서 삭제·보관(archived)된 페이지는 미러에서도 제거하고 그 사실을
  동기화 리포트에 남긴다.
- **FR2.5** 변환 불가 블록은 조용히 버리지 않고 `<!-- notion: unsupported <type> -->`
  주석으로 위치를 남긴다. 페이지 멘션은 미러 내 상대 링크로, 외부 링크는 그대로 둔다.
  Notion 호스팅 이미지 URL 은 **만료된다**는 사실을 주석으로 함께 남긴다.
- **FR2.6** 동기화는 **읽기만** 한다. Notion 의 어떤 페이지도 수정하지 않는다.
- **FR2.7** 동기화 결과 리포트(추가/변경/삭제/제외/실패 목록)를 표준출력과
  `raw/.sync-report.md` 로 남겨, 다음 단계(ingest)가 **무엇이 바뀌었는지**만 보고 일할 수 있게 한다.

### FR3 — 위키 합성 (스킬 워크플로 `ingest`)

- **FR3.1** 스킬은 동기화 리포트의 **변경분만** 읽어 위키를 갱신한다. 전체 재합성은
  운영자가 명시적으로 요청할 때만 한다.
- **FR3.2** 위키 페이지 종류와 상한은 [DESIGN 3절](./DESIGN.md#3-위키-페이지-종류와-템플릿)을 따른다:
  **서비스 개요**(서비스당 1), **카테고리 다이제스트**(서비스×카테고리당 1),
  **토픽 페이지**(카테고리를 가로지르는 주제, 필요할 때만), **충돌/미확정 페이지**(서비스당 1).
- **FR3.3** 위키의 모든 서술은 **출처**(raw 경로 + Notion URL + 원본 `상태`)를 단다.
  출처가 `초안` 이면 서술에도 `(초안)` 을 붙인다.
- **FR3.4** 원본들이 **서로 모순**되면 어느 한쪽을 고르지 않고 충돌 페이지에 양쪽을
  출처와 함께 기록한다. 해소는 사람이 원본을 고쳐서 한다.
- **FR3.5** 합성 후 `wiki/index.md` 와 `wiki/log.md` 를 갱신한다. index 는 스크립트가
  frontmatter 로 만들고, log 는 스킬이 "무엇을 왜 바꿨는지" 를 덧붙인다.

### FR4 — 질의 (스킬 워크플로 `query`)

- **FR4.1** 질문이 오면 스킬은 ① `wiki/index.md` 를 읽고 → ② 관련 위키 페이지를 읽고 →
  ③ 필요하면 `raw/` 를 grep 해 원문을 확인한 뒤 답한다. **임베딩·벡터 검색을 쓰지 않는다.**
- **FR4.2** 답변에는 **출처 목록**(Notion URL)과 **동기화 시각**을 붙인다. 위키가 오래됐을 수
  있음을 독자가 알 수 있어야 한다.
- **FR4.3** 답을 못 찾으면 "없다" 고 말하고, 어디를 봤는지 적는다. 추측으로 채우지 않는다.
- **FR4.4** 유용한 답변은 운영자 판단으로 위키 토픽 페이지로 **환류**할 수 있다
  (질문이 반복되면 위키가 자란다).

### FR5 — lint

- **FR5.1** **구조 lint(스크립트)**: frontmatter 필수 항목 누락, 허용되지 않은 값,
  깨진 내부 링크, 고아 위키 페이지(index 에 없음), 출처 없는 위키 서술 블록, `검토기한` 경과,
  위키가 참조하는 raw 가 미러에서 사라진 경우.
- **FR5.2** **의미 lint(스킬)**: 같은 주제를 다루는 raw 간 모순, 위키 서술과 원본의 불일치,
  요약 속성과 본문의 불일치. 결과는 충돌/미확정 페이지에 반영한다.
- **FR5.3** lint 는 **수정하지 않고 보고만** 한다. 결과는 두 등급이다 — **오류**(저장소가 깨진 것: 잘못된 frontmatter·허용값 밖·깨진 링크·고아 위키·출처 없음·크기 초과)는 종료 코드 1 로 CI 를 실패시키고, **경고**(사람이 Notion 에서 처리할 운영 신호: meta 없는 레거시 페이지·검토기한 경과)는 종료 코드 0 이다. 경고는 위키의 충돌·미확정 페이지가 사람에게 보여 준다. `--strict` 로 경고도 실패로 취급할 수 있다.

### FR6 — Markdown → Notion 게시 (`publish`)

- **FR6.1** `wiki/` 의 페이지를 설정된 **위키 루트 페이지** 아래에 Notion 페이지로 만든다.
  트리: 위키 루트 → 서비스 → (개요 · 카테고리 다이제스트 · 토픽 · 충돌) + 루트 바로 아래 `색인`.
- **FR6.2** **멱등**: 같은 위키를 두 번 게시하면 페이지가 두 개 생기지 않는다.
  파일→페이지 id 매핑은 `wiki/.publish-state.json` 에 남긴다. 갱신은 기존 페이지의 블록을
  교체하는 방식으로 하여 **URL 이 바뀌지 않게** 한다.
- **FR6.3** 게시기는 **위키 루트 아래에서 자기가 만든 페이지만** 수정한다.
  매핑에 없는 페이지, 루트 밖의 페이지는 어떤 경우에도 건드리지 않는다. 원본(raw) 페이지는
  게시기의 대상이 아니다.
- **FR6.4** 게시된 모든 페이지 상단에 **"이 페이지는 LLM wiki 가 자동 생성·갱신한다.
  직접 수정하면 다음 게시 때 덮어써진다. 의견은 페이지 코멘트로"** 콜아웃을 넣는다.
- **FR6.5** 기본 실행은 **dry-run** 이다. 실제 쓰기는 `--apply` 를 붙여야 한다.
  dry-run 은 만들/바꿀 페이지와 블록 수를 보고한다.

### FR7 — 스킬 패키징

- **FR7.1** `.claude/skills/notion-llm-wiki/SKILL.md` 하나로 `sync`/`ingest`/`query`/`lint`/`publish`
  를 인자로 분기한다. 절차·규칙의 상세는 `references/` 로 나눠 필요할 때만 읽게 한다.
- **FR7.2** 이 저장소를 clone 하면 그대로 위키 작업 공간이 된다 (`raw/`, `wiki/`, 설정 파일,
  스킬). 다른 저장소에서 쓰려면 스킬 디렉터리를 복사하고 설정 파일을 채운다.
- **FR7.3** 스크립트는 Node.js 22+ 내장 기능만 쓴다 (`fetch`, `node:test`, `node:fs`).
  `npm install` 이 필요 없다.

## 5. 데이터 / 보안 요구사항 (DR)

- **DR1** Notion 토큰은 `.env` 의 `NOTION_TOKEN` 으로만 받는다. `.env` 는 gitignore. 로그·리포트·
  상태 파일에 토큰을 남기지 않는다.
- **DR2** `비밀등급 = 민감` / `위키제외` 페이지는 미러·위키·색인 어디에도 남지 않는다 (FR2.3).
  기본값은 `내부` 이며, **속성이 비어 있으면 동기화한다** — 단 이 기본값이 안전한지는 조직이
  판단해야 하므로 설정으로 뒤집을 수 있게 한다 (`excludeWhenUnset`).
- **DR3** 위키는 **단일 독자 집단**을 가정한다. 동기화 범위 안의 모든 페이지는 위키 독자 모두가
  볼 수 있어야 한다. 권한이 다른 페이지가 섞이면 `민감` 으로 표시해 빼는 것이 이 샘플에서의
  유일한 수단이다 (→ 8절).
- **DR4** 동기화기는 Notion 에 **쓰지 않는다.** 게시기는 위키 루트 아래 **자기가 만든 페이지**에만
  쓴다. 두 스크립트가 같은 토큰을 쓰더라도 이 경계는 코드로 강제한다 (매핑 + 마커 확인).
- **DR5** 담당자(people 속성)는 **이름만** 미러에 남긴다. 이메일·user id 는 남기지 않는다.
  샘플 데이터의 사람 이름은 전부 가상이다.
- **DR6** 샘플 데이터는 가상 서비스·가상 내용이다. 실제 heybit 의 서비스명·정책·수치를
  넣지 않는다 (사용자 결정, 2026-09-09).
- **DR7** 게시기는 Notion API 의 한도(요청당 블록 100개, rich text 2,000자, 초당 요청 수)를
  넘지 않게 분할·대기한다. 429 는 `Retry-After` 를 존중해 재시도한다.

## 6. Acceptance 기준

실제 Notion 워크스페이스에는 연결하지 않는다 (사용자 확인, 2026-09-09). 따라서 Notion API 를
호출하는 경로는 **기록된 응답(fixture)** 으로 검증하고, 실제 Notion 에 대한 동작은 **미확정**으로
남긴다. "될 것 같다" 는 통과가 아니다 — 아래 각 항목은 **실제로 실행**해서 확인한다.

| # | 대상 | 통과 조건 |
|---|---|---|
| A1 | FR2.1 | fixture 워크스페이스(서비스 2 × 카테고리 6, 페이지 ≥ 12, 레거시 등록 항목 포함)를 동기화 → `raw/` 트리와 각 파일이 golden 파일과 **바이트 단위로 일치** |
| A2 | FR2.2 | 같은 fixture 로 2회 동기화 → 2회차 API 호출(블록 조회)이 **0건**, 리포트에 변경 0 |
| A3 | FR2.2 | 페이지 하나의 `last_edited_time` 만 바꾼 fixture → 그 페이지만 다시 받고 나머지는 건너뜀 |
| A4 | FR2.3 / DR2 | `민감` 페이지가 미러에 **없음**; 기존 미러 파일이 민감으로 바뀐 경우 **삭제됨** |
| A5 | FR2.4 | archived 페이지가 미러에서 제거되고 리포트에 남음 |
| A6 | FR2.5 | 지원 블록 전 종류(문단·제목 3단·글머리·번호·체크·토글·인용·콜아웃·코드·표·구분선·이미지·페이지 멘션·링크·동기화 블록·컬럼)가 golden Markdown 과 일치. 미지원 블록은 주석으로 위치 보존 |
| A7 | FR1.4 | 레거시 등록 항목의 `원본` 링크를 따라가 본문을 가져오고, frontmatter 의 `source_url` 이 **원본** 을 가리킴 |
| A8 | FR3.5 | `raw/`+`wiki/` frontmatter 로 만든 `index.md` 가 golden 과 일치하고, **두 번 만들어도 같음**(결정적) |
| A9 | FR5.1 | 결함 종류별로 하나씩 심은 샘플 사본 각각에서 lint 가 **정확히 그 결함**만 추가로 보고한다. 저장소 결함(L2·L3·L4·L5·L7·L8)은 **오류**(종료 코드 1), 운영 신호(L1 meta 없음·L6 검토기한 경과)는 **경고**(종료 코드 0, `--strict` 면 1). 샘플 저장소 자체는 **오류 0** 이며 경고는 의도된 것만 있다 |
| A10 | FR6.1 | 샘플 위키를 dry-run 게시 → 생성될 페이지 트리와 블록 JSON 이 golden 과 일치 |
| A11 | FR6.2 | mock 서버에 `--apply` 로 2회 게시 → 페이지 생성 요청은 1회차에만, 2회차는 블록 교체만; 페이지 수 불변 |
| A12 | FR6.3 / DR4 | 매핑에 루트 밖 페이지 id 를 심어도 게시기가 **거부**하고 종료 |
| A13 | DR7 | 블록 250개·문단 5,000자 위키 페이지 → 요청 분할(100개/2,000자) 이 golden 과 일치; mock 429 + `Retry-After` 에 대기 후 재시도 |
| A14 | FR4 | 샘플 위키에 대해 질문 3개(카테고리 내부 1, 교차 1, 위키에 없는 것 1)를 스킬 절차로 실제 수행 → 출처 URL 포함, 없는 질문엔 "없다" + 찾아본 위치. **LLM 실행 기록**으로 LOG 에 남김 |
| A15 | FR7 | `SKILL.md` frontmatter 가 규약을 만족하고, 5개 서브커맨드가 각자 절차 문서를 가리킴 (구조 검사 스크립트로 확인) |
| A16 | 재현성 | 저장소 clone → `npm test` **만으로** A1~A13 재현. `npm install` 불필요 |
| A17 | 문서 | 실무자가 [DESIGN 1·2절](./DESIGN.md)만 보고 새 페이지를 만들 수 있고, 운영자가 README 만 보고 `sync → ingest → publish` 순서를 따라갈 수 있다 (자체 점검) |

**실제 Notion 에 대한 미확정 항목** (토큰 확보 후 해소):
- 실 API 응답이 fixture 와 다른 경우 (특히 `2025-09-03` 버전의 data source 형태)
- rate limit 의 실제 임계와 `Retry-After` 값
- 블록 교체 방식 게시 시 기존 페이지 코멘트가 유지되는지 (블록 코멘트는 블록 삭제 시 사라질 것으로 예상, 페이지 코멘트는 유지될 것으로 예상 — **미실측**)

## 7. 아키텍처 방향 결정 (요약)

**결정: 원본은 Notion, 작업 공간은 로컬 Markdown 미러, 게시면은 다시 Notion.
Claude Code 스킬이 REST API 스크립트로 벌크 I/O 를 하고, 검색은 색인+grep 으로 한다.**

이유 요약:
- Notion 을 직접 매번 읽으면(MCP) 수백 페이지에서 컨텍스트와 시간을 감당할 수 없고, Notion
  검색 API 는 grep 을 대체하지 못한다. 로컬 미러는 git 이력·diff·lint 를 공짜로 준다.
- 실무자는 Notion 을 벗어나지 않으므로 위키는 Notion 에 **게시**되어야 한다. 게시는 블록 변환기가
  필요하고, 이것은 어차피 동기화기의 역방향이다.
- 수십~수백 페이지에서 색인 1장은 한 번에 읽을 수 있는 크기다. 벡터 검색은 이 규모에서
  얻는 것보다 잃는 것(인프라·청킹·근거 추적)이 많다.

상세 근거(후보안, 반론과 처리, 미확정 항목)는 [TRD 의 ADR-001~005](./TRD.md#adr) 에 3단 사고 형식으로 기록한다.

## 8. Out of scope (범위 밖) — 이유와 함께

"못 해서 안 한 것" 이 아니라 **"이 샘플의 목적을 흐리기 때문에 뺀 것"** 이다.

| 항목 | 왜 뺐는가 | 향후 경로 |
|---|---|---|
| 권한(ACL) 을 반영한 답변 | 누가 묻는지에 따라 답을 다르게 주려면 Notion 권한 모델을 미러에 복제해야 한다. 이 샘플은 "위키 독자 = 동기화 범위 열람자" 단일 집단을 가정한다. | 서비스/카테고리 단위로 위키를 분리 운영. **미확정** |
| 실시간 동기화 (webhook) | Notion 은 webhook 을 제공하지만, 이 샘플의 주기(하루 몇 번 `sync`)에서는 폴링으로 충분하고, 서버를 하나 더 띄워야 한다. | webhook → 큐 → `sync`. **미확정** |
| 임베딩/벡터 검색 | 이 프로젝트의 주제가 "RAG 없이" 다. 수천 페이지를 넘으면 재검토 ([TRD ADR-002](./TRD.md#adr-002--rag-없이-검색-가능한-구조) 임계값). | 색인 분할 먼저, 그다음 검토 |
| Notion 외 원본 (Slack, Google Docs, 코드 저장소) | raw 계층에 어댑터를 추가하는 문제. 구조는 열어 두되 구현하지 않는다. | `sources/` 어댑터 추가 |
| 원본 페이지 자동 수정 (meta 자동 채움 등) | 동기화기는 읽기 전용이어야 신뢰할 수 있다. AI 가 원본을 고치기 시작하면 "무엇이 사람 판단인가" 가 흐려진다. | 제안을 코멘트로 남기는 방식. **미확정** |
| 이미지·첨부파일 다운로드 | Notion 파일 URL 은 만료된다. 저장하려면 별도 스토리지가 필요하다. | 필요 시 `assets/` 로 내려받기 |
| 코멘트 동기화 | 위키 페이지에 달린 코멘트(정정 요청)를 읽어 ingest 에 반영하면 좋지만, 코멘트 API 와 블록 교체의 상호작용을 실측하지 못했다. | `GET /v1/comments` 로 수집 → ingest 입력. **미확정** |
| Notion 데이터베이스 자동 생성 | 카테고리 DB 스키마를 API 로 만들 수는 있으나, 조직마다 기존 DB 가 있을 수 있어 **문서와 수작업 절차**로 제공한다. | `scripts/create-db.js`. **미확정** |
| 다국어 | 샘플은 한국어. 속성 이름은 설정으로 바꿀 수 있게 한다. | 설정 파일의 속성 매핑 |

## 부록 — 용어

- **raw** : Notion 원본 페이지의 Markdown 미러. 동기화기만 쓴다. 사람은 Notion 에서 원본을 고친다.
- **wiki** : raw 를 읽고 합성한 페이지. 스킬(Claude Code)만 쓴다.
- **index** : 모든 raw/wiki 페이지의 한 줄 요약 색인. 질의의 시작점.
- **ingest** : raw 변경분을 읽어 wiki 를 갱신하는 스킬 절차.
- **다이제스트(digest)** : 한 서비스의 한 카테고리에서 "지금 알아야 할 것" 을 모은 위키 페이지.
- **토픽(topic)** : 카테고리를 가로지르는 주제 하나를 다루는 위키 페이지 (예: 환불 정책).
- **레거시 등록 항목** : 기존 일반 페이지를 옮기지 않고, 카테고리 DB 에 meta 와 `원본` 링크만 담아 만든 항목.
- **golden 파일** : 기대 출력을 저장한 파일. 테스트는 실제 출력과 골든의 일치를 확인한다.
